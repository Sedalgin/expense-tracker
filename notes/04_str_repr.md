# `__str__` и `__repr__`

## Что это
**Магические методы** (dunder, от *double underscore* — `__имя__`). Python вызывает их **сам** в нужный момент.

| Метод | Для кого | Когда вызывается |
|---|---|---|
| `__str__` | для **пользователя** | `print(obj)`, `str(obj)`, f-строка `f"{obj}"` |
| `__repr__` | для **программиста** | консоль, отладчик, `print([obj])` (внутри списка), ошибки pytest |

Без них: `<expense.Expense object at 0x0000021A...>` — бесполезно.

## Код из проекта (`expense.py`)
```python
def __str__(self):
    return f"{self.category} = {self.amount} грн"

def __repr__(self):
    return f"Expense('{self.category}', {self.amount})"
```
```python
e = Expense("Кофе", 50)
print(e)              # Кофе = 50 грн
print([e])            # [Expense('Кофе', 50)]
f"Расход: {e}"        # Расход: Кофе = 50 грн
```

## Правила
- `__repr__` выглядит **как код**, который создаёт такой же объект (можно скопировать в Python).
- Строки — в кавычках `'Кофе'`, числа — без. Пробел после запятой (PEP 8).
- Если в строке может быть апостроф (`McDonald's`) — используй `{self.category!r}`, Python сам поставит правильные кавычки.
- В тестах проверяют через `str(obj)` и `repr(obj)`, а не `obj.__str__()`.

## Зачем, если «и так работает»
1. Понятные ошибки в pytest: `[Expense('Кофе', 50)] == [Expense('Кофе', 500)]` вместо адресов в памяти.
2. Python сам знает, где вызвать: `print`, f-строки, списки.
3. Общий стандарт — любой программист ожидает именно эти имена, а не `get_expense_1`.

> Код пишут один раз, а читают и отлаживают — много раз.

## ❓ Вопрос с собеседования
**Чем `__str__` отличается от `__repr__`?**
<details><summary>Ответ</summary>

`__str__` — читаемый текст для пользователя (`print`). `__repr__` — однозначное представление для программиста, в идеале — код, создающий такой же объект. Используется в консоли, отладке, внутри списков.
</details>
